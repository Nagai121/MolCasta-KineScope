- 実軌道の変換済みデータ: 6タンパク質×3レプリカ＝18軌道（各1,001フレーム、100 ps 間隔）がこの仮想マシンの `~/workspace/gpt-model-check/data/trajectories/` にあり、MiniTopol の Registry でそのまま読めることを確認した。

- 弾性モードや局所座標など生成に要る部品のコード: ブランチ内に全部ある。

### 欠けているもの・作る必要があるもの

1. **起点を1つに固定する受け渡しコード**。元の `prepare` はシャードの多数の起点を前提にしており、資料Dの「起点＝1 ns の1フレーム」ではそのまま使えない。候補の作り方（起点で 3.5〜6.0 Å、別残基どうし）は資料Dのコードと同じ定義にそろえて部品へ渡す必要がある。
2. **特徴量の対応の決定**。生成経路は 0.1、0.3、0.5、1.0 ns の4時点しかない。資料Dの履歴特徴6個（最初、平均、標準偏差、最小、最後−最初、3.5 Å 以下の割合）は11フレームから作る定義なので、生成側は「起点＋4時点の5点」で同じ6個を作る近似にするか、元の8特徴を静的特徴に足す形にするか、先に決めて固定する必要がある。前者を推す（実軌道側と読み出しをそろえるのが K06 の目的のため）。その場合、実軌道側も5点に間引いた条件を対照として併記する。
3. **データの置き場の違いの吸収**。元のコードは `atlas-workspace/<タンパク質>/` 形式の Registry を前提にする。この仮想マシンのデータは1つのワークスペースに18軌道が入った形式なので、Registry の向け先を変える小さい修正が要る。
4. 生成器の**再学習はしない**（保存済みチェックポイントを使う）。再学習が必要になった場合は学習が CUDA 前提（`fit` が CUDA なしではエラー）なので Colab の T4 が要る。

### 計算量の見込み

候補は6タンパク質×3レプリカで約14,600件（K05 で実測）。元の実験では第21〜25案の特徴生成と推論が約33万候補行で CPU 57秒（記録値）なので、この規模なら仮想マシンの CPU で分単位。判別器の学習し直しも予測幅6条件×入力条件数で軽い。Colab は不要な見込み。

### 条件をそろえるときの注意

- 資料Dの学習4タンパク質のうち 1bgf_A は元の第22案の判別器の学習側にも入っているが、K06(a) では判別器を資料Dの条件で学習し直すので問題にならない。生成器の教師とは重ならない。
- 元の第22案の起点は軌道の多数の時刻だが、K06(a) の起点は 1 ns 固定。生成されるのは起点から先（0〜1 ns）の経路で、資料Dの実履歴（起点までの 0〜1 ns）とは向きが違う。これは「単一構造から先を生成して、過去の実履歴の代わりにする」という元の問いそのものなので、比較の定義として明記する（実履歴条件が「過去」、生成条件が「未来の生成」で、どちらも 1 ns 先以降のラベルの予測に使う）。

### 欠けているもの・未検証のもの

1. **本体 T1I2006 の依存関係の完全な確認ができていない**。T1I2006 は「アンサンブルの重み付き平均」であり、その要素自体が較正つきの混合モデルで、部品が複数の実験ディレクトリに分散している。今回の確認では代表的な部品の実在までは追えたが、全依存をたどり切ってはいない。実験コードは「部品がちょうど2つあること」と「推論を1回強制してハッシュを検証する」作りなので、実際に `prepare_model` を動かすまでは「全部そろっている」とは言えない。**これが (b) の最大の未確定点**で、先に小さく検証すべき。
2. **評価・較正に使う軌道データが手元にない**。100＋8タンパク質の ATLAS 軌道はこの仮想マシンになく、元のコードの `acquire` で ATLAS から取得し直して MiniTopol 変換する必要がある（108タンパク質×3レプリカ）。
3. **起点を1つに固定する受け渡しコード**。(a) と同じものが要る。資料Aの候補は `predict_snapshot` が起点（1 ns）の構造から作るので、候補の同一性を保ったまま生成特徴を横に足す形になる。
4. **特徴量の対応の決定**。資料Aの履歴特徴10個は11フレームの系列から作る。生成側は5点（起点＋4時点）で同じ10個を作る近似にするか、生成の8特徴を補正モデルの入力に足す形にするか。実履歴側の保存済み予測は候補の並び順が再現できた場合だけ流用でき、生成条件の追加には結局 `one_replica` 相当の再実行が要る。

### 計算量の見込み

元の100配列実験は GitHub Actions で25タンパク質ずつ4分割して実行された規模。軌道の取得と変換、本体の推論（108タンパク質×3レプリカ×911フレーム）、生成の推論を合わせると、仮想マシンの CPU だけでは重く、Colab（無料枠、T4）と組み合わせても取得・変換が律速になる見込み。(a) で受け渡しコードと特徴量の対応を固めてから (b) に進むのが順序として妥当。

## 5. 結論

- (a) 資料D条件への再比較は**実現可能**。欠けているのはデータやチェックポイントではなく、起点固定の受け渡しコードと特徴量の対応の決定だけ。計算も軽い。

### 条件

- 土台は凍結した T1I2006。その上に補正モデル（HistGradientBoosting、

### 読み

資料A条件では、生成した軌道の特徴は補正に何も足さない。実履歴が
確かに効く（+0.027〜+0.071）のに対し、生成はゼロ付近で、短い予測幅
ではむしろ少し悪い。強い土台（凍結した本体）の上では、生成が持つ
情報は静的特徴にすでに含まれている平均距離のずれだけで、動きの
情報は補正に届いていない。

これは (a) の結果と並べると意味がはっきりする。(a) の弱い土台
（資料Dの再学習モデル）では生成は 1 ns 先で +0.036 の改善を見せた。
土台が弱いときは生成の平均距離のずれが役に立つが、土台が強い
（凍結した本体＋補正）と、そのずれは静的特徴がすでに吸収していて、
残るものがない。提案第22案の「指導力」は、土台の強さに依存する
見かけのものだった、というのが (b) の結論である。
