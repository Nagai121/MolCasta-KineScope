## 2. 機構実験・第22案の実装

### コードの場所

### 生成の仕組み（入力 → 出力）

- 教師（学習時だけ）: 判別器の学習・検証と分離した8タンパク質（1u84_A、4u5h_G、5hub_A、1x6j_A、2y1y_A、1krn_A、2y4x_B、4xqm_A）について、起点から 0.1、0.3、0.5、1.0 ns 先の実MD座標を MiniTopol から読み、候補ペアの局所座標（ドナー、アクセプター、ドナー側の結合相手、アクセプター側の結合相手、競合アクセプターの5サイトを、ドナー→アクセプター軸の局所座標系で表したもの）の変位を教師とする。教師行数は 110,464 行。
- 初期推定: 起点構造の Cα 座標から距離ばねモデルの Hessian の低周波モードを作り、残基運動の経路を生成して局所座標へ写す（`mode_paths` の信号から 4 時点分）。
- 学習する部分: 小さなニューラルネット（入力110次元 → 112 → 96 → 出力424）が、(1) 教師経路の平均とばらつき、(2) 初期推定への補正、(3) 状態遷移、(4) 拘束つき経路、の4系統を同時に出す。第22案が使うのは (2) の補正で、「初期推定（弾性モード）＋学習した補正」を結合長拘束つきで局所座標に戻したものが第22案の生成経路になる。学習は CUDA で 16 エポック、約6.1秒（記録値）。
- 生成器への入力（推論時）: 起点1フレームだけから作る110次元（候補ペアの列3個、静的特徴の先頭24個、局所サイト座標15個、directional 特徴8個、弾性モード経路60個）。
- 生成の出力: 候補ごとに 4 時点（0.1、0.3、0.5、1.0 ns）の局所座標経路が1本（標本ではなく決定論的な経路）。座標そのものは保存されず、その場で次の8特徴に要約される。

### 判別器との接続

- 要約（`summarize` 関数）: 生成経路からドナー・アクセプター距離の系列を作り、8個の数値にする（距離変化の平均、標準偏差、最小、最大、3.5 Å 以下だった割合、4.0 Å 以下だった割合、最終時点の距離変化の平均、距離が減ったステップの割合）。
- 判別器: XGBoost（深さ6）を学習し直す比較。入力は静的特徴118個＋表現の追加8個＋上記の生成8個を差し込む形（`search_events.view` の `hb-origin-stacked-learnedcoord22`）に、local・directional・cloud・occupied の各ブロックを続けたもの。学習は12タンパク質・179,984候補、検証は固定10タンパク質・153,212候補。
- 凍結した T1I2007 への接続は予測の混合だけ（差分を 3.125% 加えた条件が最良でも AUPRC +0.00000689 で、独立した改善の証拠なし）。

## 3. そろえ先 (a) 資料Dの条件 ― 実現可能（部品はそろっている。つなぐコードが要る）

資料Dの条件: 6タンパク質（学習 1bgf_A、1ifg_A、1j8r_A、2b0a_A／テスト 1mix_A、2qt4_A）×3レプリカ、起点 1 ns、履歴 0〜1 ns、静的特徴は現象ごとに5〜7個、HistGradientBoosting を条件ごとに学習し直す。対象はまず水素結合形成に限るのが自然です（第22案は水素結合専用の仕組みです）。

### 実在するもの

- 資料Dの実験コード `fixed_1ns_history_3phen_6h.py` と土台 `atlas_minitopol_models.py`: 資料Dのブランチにある（11,641 バイト／14,439 バイト）。結果は GitHub Actions の成果物（run 44883044790、5,471 バイト）が未期限で残っている。
- 実軌道の変換済みデータ: 6タンパク質×3レプリカ＝18軌道（各1,001フレーム、100 ps 間隔）がこの仮想マシンの `~/workspace/gpt-model-check/data/trajectories/` にあり、MiniTopol の Registry でそのまま読めることを確認した。
- 生成器のチェックポイント（上記）: 推論は CPU で動く形（`prepare_features` は CPU 推論）。この仮想マシンには GPU がないが、推論だけなら足りる。教師8タンパク質は資料Dの6タンパク質と重ならないので、生成器側からの情報の混入はない。
- 弾性モードや局所座標など生成に要る部品のコード: ブランチ内に全部ある。

### 欠けているもの・作る必要があるもの

1. **起点を1つに固定する受け渡しコード**。元の `prepare` はシャードの多数の起点を前提にしており、資料Dの「起点＝1 ns の1フレーム」ではそのまま使えない。候補の作り方（起点で 3.5〜6.0 Å、別残基どうし）は資料Dのコードと同じ定義にそろえて部品へ渡す必要がある。
2. **特徴量の対応の決定**。生成経路は 0.1、0.3、0.5、1.0 ns の4時点しかない。資料Dの履歴特徴6個（最初、平均、標準偏差、最小、最後−最初、3.5 Å 以下の割合）は11フレームから作る定義なので、生成側は「起点＋4時点の5点」で同じ6個を作る近似にするか、元の8特徴を静的特徴に足す形にするか、先に決めて固定する必要がある。前者を推す（実軌道側と読み出しをそろえるのが K06 の目的のため）。その場合、実軌道側も5点に間引いた条件を対照として併記する。
3. **データの置き場の違いの吸収**。元のコードは `atlas-workspace/<タンパク質>/` 形式の Registry を前提にする。この仮想マシンのデータは1つのワークスペースに18軌道が入った形式なので、Registry の向け先を変える小さい修正が要る。
4. 生成器の**再学習はしない**（保存済みチェックポイントを使う）。再学習が必要になった場合は学習が CUDA 前提（`fit` が CUDA なしではエラー）なので Colab の T4 が要る。

### 計算量の見込み

候補は6タンパク質×3レプリカで約14,600件（K05 で実測）。元の実験では第21〜25案の特徴生成と推論が約33万候補行で CPU 57秒（記録値）なので、この規模なら仮想マシンの CPU で分単位。判別器の学習し直しも予測幅6条件×入力条件数で軽い。Colab は不要な見込み。

### 条件をそろえるときの注意

- 資料Dの学習4タンパク質のうち 1bgf_A は元の第22案の判別器の学習側にも入っているが、K06(a) では判別器を資料Dの条件で学習し直すので問題にならない。生成器の教師とは重ならない。
- 元の第22案の起点は軌道の多数の時刻だが、K06(a) の起点は 1 ns 固定。生成されるのは起点から先（0〜1 ns）の経路で、資料Dの実履歴（起点までの 0〜1 ns）とは向きが違う。これは「単一構造から先を生成して、過去の実履歴の代わりにする」という元の問いそのものなので、比較の定義として明記する（実履歴条件が「過去」、生成条件が「未来の生成」で、どちらも 1 ns 先以降のラベルの予測に使う）。

## 4. そろえ先 (b) 資料Aの条件 ― 部品はほぼあるが、規模と未検証の依存関係が重い

資料Aの条件: 凍結した本体 T1I2006＋補正モデル（HistGradientBoosting、予測幅ごとに学習）、補正の学習は別8タンパク質、評価は未見100タンパク質×3レプリカ、候補 163,074 件。履歴特徴は候補ペア自身の距離系列からの10個。

### 実在するもの

- 実験コード `tseries/t1i2006_initial_history_100.py`（16,602 バイト）と集計コード、ワークフロー: 資料Aのブランチにある。
- 実履歴条件の結果と予測: `analysis/initial_trajectory_effect/raw/atlas100/predictions_*.npz`（6予測幅分）と `results_100.json` が資料Aのブランチに保存されている。
- 本体 T1I2006 の構成記録: `selections/T1I2006/selection.json` に重み（T1I1451 が 0.90625、T1I1453 が 0.09375）がある。構成要素の記録（`ensemble_gate/T1I1451.json`、`T1I1453.json`、較正の記録 `ensemble_calibration/T1I1321.json` など）と、一部の実モデル（`stacked_volume/T1I1281.ubj`、`stacked_dense_origins/T1I1361.ubj` など）はブランチ内にある。
- 補正モデルの学習コード（`learner` 関数、木160本など）: 実験コード内にある。
- 生成器のチェックポイント: (a) と同じものが使える。教師8タンパク質は資料Aの較正8タンパク質・評価100タンパク質と重ならない。

### 欠けているもの・未検証のもの

1. **本体 T1I2006 の依存関係の完全な確認ができていない**。T1I2006 は「アンサンブルの重み付き平均」であり、その要素自体が較正つきの混合モデルで、部品が複数の実験ディレクトリに分散している。今回の確認では代表的な部品の実在までは追えたが、全依存をたどり切ってはいない。実験コードは「部品がちょうど2つあること」と「推論を1回強制してハッシュを検証する」作りなので、実際に `prepare_model` を動かすまでは「全部そろっている」とは言えない。**これが (b) の最大の未確定点**で、先に小さく検証すべき。
2. **評価・較正に使う軌道データが手元にない**。100＋8タンパク質の ATLAS 軌道はこの仮想マシンになく、元のコードの `acquire` で ATLAS から取得し直して MiniTopol 変換する必要がある（108タンパク質×3レプリカ）。
3. **起点を1つに固定する受け渡しコード**。(a) と同じものが要る。資料Aの候補は `predict_snapshot` が起点（1 ns）の構造から作るので、候補の同一性を保ったまま生成特徴を横に足す形になる。
4. **特徴量の対応の決定**。資料Aの履歴特徴10個は11フレームの系列から作る。生成側は5点（起点＋4時点）で同じ10個を作る近似にするか、生成の8特徴を補正モデルの入力に足す形にするか。実履歴側の保存済み予測は候補の並び順が再現できた場合だけ流用でき、生成条件の追加には結局 `one_replica` 相当の再実行が要る。

### 計算量の見込み

元の100配列実験は GitHub Actions で25タンパク質ずつ4分割して実行された規模。軌道の取得と変換、本体の推論（108タンパク質×3レプリカ×911フレーム）、生成の推論を合わせると、仮想マシンの CPU だけでは重く、Colab（無料枠、T4）と組み合わせても取得・変換が律速になる見込み。(a) で受け渡しコードと特徴量の対応を固めてから (b) に進むのが順序として妥当。

## 5. 結論

- (a) 資料D条件への再比較は**実現可能**。欠けているのはデータやチェックポイントではなく、起点固定の受け渡しコードと特徴量の対応の決定だけ。計算も軽い。
- (b) 資料A条件への再比較は**条件付きで可能**。先に本體 T1I2006 の依存関係が全部そろっているかを小さい実行で確かめる必要があり、軌道データの再取得も要る。(a) の成果物（受け渡しコード、特徴量の対応）を使い回せる。
- どちらも、生成器は保存済みチェックポイントの再利用が前提。再学習が要る場合は CUDA 環境（Colab T4）が別途必要。
